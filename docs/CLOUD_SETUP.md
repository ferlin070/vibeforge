# Optional cloud setup

Create a dedicated Supabase project; do not reuse a different product database. Review and run docs/cloud-schema.sql once in the new SQL editor. It includes explicit grants and owner-only RLS. Enable email/password auth and email confirmation, configure allowed redirect/Site URL and email delivery. Set NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY in local/Vercel environment and rebuild. Use publishable key only, never service role. No credentials in GitHub. Verify two separate accounts cannot read/write each other's rows. Access and refresh tokens stay in memory only. Refresh before expiry; failure or reload requires signing in again. Set Auth Site URL and exact allowed callback URLs to the deployed root for password recovery and confirmation. The browser handles the implicit recovery fragment, removes it from history, and presents a password update form without signing the user into the workspace. Verify recovery and resend with a test account and configured SMTP before public release. Cloud snapshots are explicit backups/restores, not automatic multi-device synchronization. Local data stays in the browser on logout. Enable auth abuse protections before public release.

## Existing environment and recovery

The audit must not create a new project, replay initial schema SQL, modify Auth settings or send real emails without approval. For an existing dedicated VibeForge environment, inspect the current schema, policies and configuration read-only before any migration. Use separate approved test users for live verification. Client validation limits project snapshots to 1,200,000 UTF-8 bytes before database checks. A cloud restore validates row identity and nested data; invalid snapshots are excluded, not deleted. Do not mistake a successful mock test for live email delivery or RLS verification.
